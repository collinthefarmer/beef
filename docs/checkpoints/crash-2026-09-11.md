# Crash at 19:15:46: inconsistent TextureLab layouts

Inputs: `crash-2026-09-11-19-15-46.log` and the corresponding
`BetterEnchantmentEffects.log`. Runtime: Skyrim 1.6.1170.

The plugin log ends with `PBR material layout check passed` at 19:15:46.132.
The crash is in `TextureLab::MeanChannel`, called by `MaterialInputs::From`
during `Manager::CollectPieces` on the SKSE task path.

The installed DLL inspected on September 12 has SHA-256
`8dbc6f2f184761c51f13ed9f5f1889882508fed69329f10ebc2d39785f3ae85c`.
Its instructions at the reported crash offset match the crash log.

## Binary evidence

Offsets below are RVAs within that DLL, not current source line numbers.

- The singleton accessor at `0x2AC390` constructs the object at `0x4B1648`
  by calling the constructor at `0x2ABD20`.
- The constructor allocates and initializes the channel-mean map's sentinel
  and stores it at `this + 0xD8` (instruction at `0x2ABDB5`).
- `MeanChannel` begins at `0x2B3500`. At `0x2B3536` it instead loads the
  supposed map sentinel from `this + 0x108`, then loads its parent pointer.
- At `0x2B3541` it tests the supposed tree node's sentinel flag at `+0x19`.
  The parent pointer is the invalid value `0x90007686F42FAEBD` in the crash.

The constructor and reader therefore disagree about the object's layout.
The reader's `0x108` matches the layout before the render-target pool was
extracted; the constructor's `0xD8` matches the current header. The reader
is interpreting another member's storage as a map. This explains the
failure without assuming an invalid height-map texture or a cache race.

The exact historical build operation that combined incompatible objects is
unknown. A subsequent clean project rebuild reproduced missing dependency
records: Ninja reported zero dependencies for `RuntimeTexturesLab.cpp.obj`
and `RuntimeTexturesReadback.cpp.obj`, while `CompositorSource.cpp.obj` had
2045 dependencies including `RuntimeTextures.h`. A header timestamp change
scheduled only the latter object. Before the clean rebuild, the readback
object did have the header in its dependency record, so the problem can
appear on a later rebuild.

The compiler launcher was ccache. Project targets now bypass it; third-party
targets retain their existing launcher. The old assumption that `/Zi` made
all plugin objects uncacheable was not sufficient to ensure reliable header
dependency records.

## Recovery

Recompile all project translation units together and link one DLL/PDB pair.
Verify the constructor and reader agree on the cache offset before staging
the result for an in-game retry. The earlier actor-reference, saved-texture,
and readback-bound checks address separate risks; they are not the diagnosis
of this crash.

## Verification after bypassing the launcher

- Release build completed successfully with four jobs and no compiler
  warnings. CMake still reports its existing skipped-install-rules warning.
- The constructor, readback, and compositor-source objects record 2039,
  2035, and 2045 dependencies respectively, each including the shared header.
- Temporarily advancing the header timestamp schedules all three objects
  in a Ninja dry run. The timestamp was restored afterward. The dry run
  uses a temporary copy of the manifest to avoid CMake's glob-verification
  regeneration obscuring the compile plan.
- The linked DLL constructor writes the sentinel at `this + 0xD8`
  (RVA `0x2AC265`) and `MeanChannel` reads it at `this + 0xD8`
  (RVA `0x2B3A06`). These were checked in the final DLL using the matching
  PDB's function addresses.
- Staged DLL SHA-256:
  `45a713d5ede4cfb2d3e2b5c36b609d69dbd5d9c3edcdc18ce7478c1b568f09e0`.
  The DLL/PDB pair is built but has not been installed or tested in game.
